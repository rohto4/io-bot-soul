## ドキュメント構成の整理

`imp-*` と `user-*` の意味を揃えた。

- `imp-*`: 実装側を主語にした作業計画、実装状況、完了記録
- `user-*`: ユーザー側の判断待ち、作業依頼、確認事項
- `diary`: セッション単位、日次単位の作業記録

これにより、ユーザーが見るべきものは `user-*`、実装側が進行を見るものは `imp-*` という読み分けにした。

この運用は今後の別PJにも持ち込める共通ルールとして、`PROJECT.md` ではなく `AGENTS.md` 側に書く方針にした。`PROJECT.md` は現状や進行中の具体タスクを書く場所であり、恒久ルールを置きすぎないようにした。

## `candi-ref` / `spec` / `guide` の定義整理

`docs/candi-ref`、`docs/spec`、`docs/guide` の境界も整理した。

- `docs/candi-ref`: 候補、比較、調査、未採用案、判断前の材料
- `docs/spec`: 採用済みで、実装や運用の前提になる仕様
- `docs/guide`: 実行手順、運用手順、判断基準、AI/人間向けの作業ガイド

当初は各フォルダを最大10ファイル程度に収める前提で整理を検討したが、`spec` は無理に10ファイルへ圧縮すると1ファイルが大きくなりすぎる見込みだった。

最終的には、このPJはソースコード量が比較的小さく、仕様領域も明確に分けやすいため、`docs/spec` は16ファイル構成にした。`docs/spec/README.md` には、この構成がこのPJの性質に合わせたものであり、別PJでは別構成になりうることを明記した。

## 投稿ログの読みやすさ改善

抽選スキップログで出ていた長い小数を丸めた。

対象は `scheduledPost.skip` の `reason: probability` で出る値。

- `elapsedMinutes`: 小数2桁まで
- `probability`: 小数3桁まで
- `draw`: 小数3桁まで

これにより、次のような不要に長い値を運用ログに出さないようにした。

```json
{
  "elapsedMinutes": 9.998966666666668,
  "probability": 0.1499896666666667,
  "draw": 0.6910278688700067
}
```

また、ログのタイムスタンプを日本時間表示にした。

- トップレベルの `at`
- `latestPostedAt` など `At` で終わるフィールド
- `Until` で終わるフィールド

内部処理やDB保存のUTC前提は変えず、ログ出力時だけ `+09:00` 表示にしている。

確認した実ログ例:

```json
{"at":"2026-05-06T19:59:42.638+09:00","level":"info","message":"..."}
```
